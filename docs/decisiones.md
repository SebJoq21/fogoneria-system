- [2026-09-12] Fase 3 backend = **Postgres + Prisma**. No introducir otro ORM sin revertir esto. `docker-compose.yml` local levanta PostgreSQL 16 en `localhost:5433` con `fogoneria_shadow` (tarea 58 parcial; faltan Dockerfiles y CI).
- [2026-10-19] Prisma **7.10.1** con `prisma.config.ts`, generator `prisma-client` y `@prisma/adapter-pg`; esquema PostgreSQL `fogoneria` vía `DATABASE_URL?schema=fogoneria`.
- [2026-10-19] Las migraciones en `apps/api/prisma/migrations` son la **fuente ejecutable**; `db/fogoneria_schema.sql` queda como referencia del DDL y del seed histórico.
- [2026-10-19] El seed demo vive en `apps/api/prisma/seed.ts`, usa Prisma Client y es idempotente (`skipDuplicates` + IDs deterministas).
- [2026-09-12] Auth web actual = **mock con cookies planas** (`proxy.ts` + `lib/auth.ts`). No apto para prod; la API real revalidará JWT + tenant. **[2026-10-20]** El login ya es real (`POST /auth/login`) y guarda el JWT en `localStorage["fogoneria:token"]`; las cookies de rol/branch se mantienen solo para el RBAC de `proxy.ts` y su endurecimiento (HttpOnly/firmada) queda en la tarea 55 (Joshua). **[2026-10-20] IMPLEMENTADO (tarea 55, al 95%):** el RBAC de navegación usa una cookie **HttpOnly/SameSite `fogoneria.session`** firmada con HS256 (`jose` + `SESSION_SECRET`) emitida por `app/api/session/route.ts`, con ventana deslizante de **15 min** (refresh en `proxy.ts`) y tope absoluto de **8 h**; fuera de development/test, sin `SESSION_SECRET` falla cerrado. Logout server-side (`/api/session/logout`) borra ambas cookies con 303. Roles/sucursales desconocidos fallan cerrado. **[2026-10-20] Verificado** con API + PostgreSQL (37 tests web y login real). `SESSION_COOKIE_SECURE` permite desactivar `Secure` solo en HTTP local; en producción debe quedar `true`.
- [2026-10-20] Auth API = **JWT (Passport) + bcryptjs**. El login valida usuario activo y estado del tenant (`TRIAL`/`ACTIVE`); `SUSPENDED`/`EXPIRED`/`LEAD`/`NO_CALIFICADO` y trial vencido se rechazan. Contraseña demo única: `Fogoneria123!`.
- [2026-10-20] Aislamiento multitenant de la API = **AsyncLocalStorage + Prisma Client Extension** (`prisma.scoped`), no RLS nativo todavía. SUPERADMIN opera con bypass. El RLS de PostgreSQL queda para la tarea 62; no duplicar la lógica en controllers. **[2026-10-20] AYCDS-62 + runtime:** el RLS SQL (políticas + `current_empresa_id()`/`current_sucursal_id()`/`is_bypass()`) está **forzado** en `fogoneria_db` y `fogoneria_test`. La API fija `app.empresa_id`/`app.sucursal_id`/`app.usuario_id`/`app.bypass` con `set_config(..., true)` dentro de `runWithTenant` (transacción por request). Clientes: `raw` (migraciones), `rls` (negocio), `scoped` (extensión sobre `rls`) y `fogoneria_saas` con `BYPASSRLS`. Detalle en `docs/rls-modelo.md`.
- [2026-10-20] `PrismaService` usa **composición** (`raw` + `scoped`), no herencia de `PrismaClient`: en Prisma 7 el constructor devuelve un proxy y una subclase deja `raw.usuarios` en `undefined`. No volver a extender `PrismaClient`.
- [2026-10-20] El Postgres local se publica en **5433** para convivir con otros proyectos que usan 5432; `DATABASE_URL` y `SHADOW_DATABASE_URL` deben apuntar al mismo puerto.
- [2026-10-20] La API expone **`/api/v1`** con `ValidationPipe` global y Swagger en `/api/docs`; los DTO viven junto a cada módulo. Las queries de negocio usan `scoped`; auth y consola SaaS usan `raw`.
- [2026-10-20] Ciclo SaaS: `TRIAL → EXPIRED` al vencer `trial_fin` y `EXPIRED → SUSPENDED` tras `BILLING_GRACE_DAYS` (5 por defecto), ejecutado por cron diario a las 03:00. Cada transición se audita.
- [2026-10-20] Onboarding web = **`POST /api/v1/onboarding` público** (`@Public()`): valida RUC (módulo 11) y, si no existe, crea en una transacción empresa `TRIAL` con `logo_url`, sucursal matriz, admin `ADMIN_GLOBAL`, lista de precios "Carta", lead `GANADO` y evento de auditoría. No requiere token; el alta desde la consola SaaS (tarea 61) sigue siendo autenticada. El logo viaja como data URL (no hay storage todavía), así que el body parser de Express acepta **4 MB solo en esa ruta** (`main.ts`, `bodyParser: false` + `json/urlencoded` por ruta) y el DTO acepta hasta ~2 MB de imagen.
- [2026-10-20] El **catálogo del web vive en la API** (tarea 60), no en `localStorage`: `lib/catalog-api.ts` lo lee/escribe y `ModulesProvider` lo mantiene en estado. Los `id` de catálogo son **UUID** en todo el ERP y `ErpState` es `v2` (`fogoneria:erp:v2`), sin campos de catálogo.
- [2026-10-20] RUC = **módulo 11 SUNAT** con `checkDigit = (11 - (sum % 11)) % 10` (resto 0 → 1, resto 1 → 0). El onboarding **rechaza con 400** un RUC con dígito inválido (validación de formato en el DTO, dígito en el servicio); casos de referencia en `ruc.spec.ts`. No aceptar el RUC solo por longitud.
- [2026-10-20] El alta pública **no acepta `plan`**: el DTO usa `forbidNonWhitelisted`, así que un `plan` pagado en el payload da 400 y el servicio fuerza `plan_actual: 'TRIAL'` con `mrr_monto: 0`. El plan se cambia desde la consola SaaS (tarea 61).
- [2026-10-20] `POST /onboarding` lleva **rate limit por IP en memoria** (5 intentos / 10 min, `ONBOARDING_RATE_LIMIT` y `ONBOARDING_RATE_WINDOW_MS`). El guard no se inyecta desde el módulo (`@UseGuards` + factory rompía el DI en e2e): lee las variables al construirse y expone `configure()` para tests. Multi-instancia → Redis.
- [2026-10-20] El body parser de Express se configuró **por ruta**, no global: 4 MB solo en `/api/v1/onboarding` (logo en data URL) y 100 KB por defecto para el resto. No volver a `json({ limit: '4mb' })` global.
- [2026-10-20] El **tenant y las sucursales del web salen de la API** (`lib/tenant-api.ts`): `ModulesProvider` hidrata `/tenant` + `/tenant/branches`, revalida la sucursal guardada y poda combos huérfanos tras refrescar catálogo. `DEMO_COMPANY`/`GENERAL_BRANCH` quedan como fallback. El rol `cajero` (real en la API) se agregó a `AppRole`, `proxy.ts` y al RBAC del sidebar.
- [2026-10-20] Actualización de grupos de modificadores = **sync por `id`**: el payload manda `opciones[].id` (opcional); el servicio actualiza/crea/elimina en una transacción, rechaza ids repetidos o ajenos (400) y bloquea el borrado de opciones usadas en `detalles_orden_modificadores` (409).
- [2026-09-12] Precio vive en **PriceList**, nunca en `Product`. Consumir vía `priceOf()` (`lib/erp-catalog.ts`).
- [2026-09-12] Catálogo/clientes globales; operación (órdenes/mesas/caja) **scoped por sucursal**. Vista `todas` solo agregada.
- [2026-09-12] Memoria del agente en capas: `AGENTS.md` (always-on mínimo) + `opencode.json:instructions` (referencia) + `docs/SESION.md` (sesión rotativa) + `/guardar-contexto` y `/retomar`.
- [2026-10-20] **AYCDS-62 — RLS con roles separados.** `fogoneria_app` (dueño) queda para migraciones/onboarding; `fogoneria_rls` (sin `BYPASSRLS`) para la API de negocio; la consola SaaS usa un rol con `BYPASSRLS`. `FORCE ROW LEVEL SECURITY` se activa recién cuando la API fije `app.empresa_id`/`app.sucursal_id` con `set_config(..., true)` dentro de la transacción. Nunca `SET` sin `LOCAL` con pool de conexiones.
- [2026-10-20] **AYCDS-62 — soft-delete solo en entidades maestras.** La contabilidad no se borra: se anula o se compensa. `comprobantes` usa `estado = 'ANULADA'` como baja funcional. `empresas.ruc` no se reutiliza tras la baja (trazabilidad). `opciones_modificadores` queda fuera del soft-delete porque el catálogo las elimina físicamente cuando no están referenciadas.
- [2026-10-20] **AYCDS-62 — inmutabilidad en la base, no solo en la API.** Los triggers `BEFORE UPDATE/DELETE` con SQLSTATE `45000` y códigos `DB_*` son la última línea de defensa; la API traduce el código a 409/422 (`docs/errores-db.md`). Las correcciones contables se hacen con movimientos compensatorios, nunca con `UPDATE`.
- [2026-10-20] **Email único global solo entre usuarios activos.** El índice parcial `uq_usuarios_email_activo` (`deleted_at IS NULL`) impide duplicados vigentes, pero un usuario soft-deleted libera su correo. El onboarding pre-valida el email activo antes de crear la empresa.
- [2026-10-20] **Aislamiento web por tenant.** La persistencia usa `fogoneria:erp:v2:${empresaId}`, `AppUser.empresaId` y `ModulesProvider` con estado por tenant; `BroadcastChannel` también se namespaced. El seed/demo conserva datos demo y los tenants nuevos arrancan vacíos.
- [2026-10-20] **Sesión BFF y Docker.** El BFF `app/api/backend/[...path]` exige `fogoneria.session` (401 sin sesión, 403 por `Origin` ajeno, 502 upstream); no existe `/auth/me` porque el rol del JWT es inmutable por 8 h. Dockerfiles multi-stage y Compose (`migrate` → `roles` → `api`/`web`) son la vía de despliegue local; CI ejecuta migraciones, RLS y todas las suites.
- [2026-10-21] **Los IDs demo cumplen RFC 4122.** Los DTO usan `@IsUUID()` (versión 1-8 y variante 8/9/a/b), así que el seed no puede usar IDs como `2222-2222-...`. Tercer grupo `4xxx` y cuarto `8xxx`. El seed detecta el dataset legacy y falla con instrucción de recrear el volumen; no duplica datos. Un test estático (`prisma/seed-ids.spec.ts`) impide reintroducir IDs inválidos.
- [2026-10-21] **El chequeo CSRF del BFF compara `Origin` contra `Host`/`x-forwarded-host`, no contra `nextUrl.origin`.** En Next standalone `nextUrl.origin` se arma con `HOSTNAME` (`0.0.0.0` en Docker) y rechazaba todas las mutaciones del navegador. La cookie `fogoneria.token` usa la misma regla `SESSION_COOKIE_SECURE` que la de sesión para que Compose por HTTP local funcione también fuera de `localhost`.
- [2026-10-21] **Única excepción pública del BFF: `POST /onboarding`.** El wizard de alta no tiene sesión; el BFF reenvía solo esa ruta (la API la marca `@Public()` y aplica rate limit). Cualquier otra ruta, incluida `POST /onboarding/otro`, sigue exigiendo la cookie firmada. No ampliar esta lista sin revisar el rate limit del endpoint.
- [2026-10-28] **AYCDS-25 — Las comandas del web salen de la API; las cuentas siguen locales.** Con sesión real, `ModulesProvider` hidrata `orders` desde `GET /orders` y las mutaciones pasan por `POST /orders` y `PATCH /orders/:id/status`; sin sesión (demo) se mantiene el estado local. La "cuenta" (`TableAccount`) sigue en `localStorage` porque no hay API de cuentas: es el carrito del mesero y **una comanda = un `POST /orders`** con las líneas no enviadas. El KDS ya no muta estado local. `lib/order-mapping.ts` es el único punto de traducción (estados, folio como `id`, `apiId` para los PATCH, `mesero_id` → `waiterId`).
- [2026-10-28] **AYCDS-25 — Los modificadores viajan como nota, sin recargo.** `OrderItemDto` no acepta modificadores ni precio: el importe lo resuelve el servidor (AYCDS-20) y los nombres de los modificadores se concatenan en `notas` (tope de 500 caracteres). El recargo (`extra > 0`) se sigue cobrando en Caja, que trabaja con la cuenta local; el alta de líneas lo advierte. Si se quiere recargo en la comanda, hace falta un Jira de API (`items[].modificadores`).
- [2026-10-28] **AYCDS-25 — La mesa del mesero se elige de la API.** `GET /tables` devuelve UUID, así que `TableAccount` gana `tableApiId` (lo que viaja como `mesaId`) y `Table` gana `apiId` **sin cambiar** su `id` numérico: el mapa de mesas y `deriveTableStatus` (AYCDS-26) siguen funcionando igual.
- [2026-10-28] **Folios por empresa en la tabla `secuencias`** (AYCDS-16/20, ajustado en AYCDS-22). `(empresa_id, tipo, valor)` se incrementa con `INSERT ... ON CONFLICT ... RETURNING`. Nada de `Date.now()` ni `COUNT(*)`: ambos se repiten bajo concurrencia o tras borrados. `numero_orden` pasa a `ORD-000123` y el `codigo` de reserva a `RSV-YYYYMMDD-NNNN`. **El upsert corre en autocommit sobre el pool de plataforma (`prisma.raw`), fuera de la transacción del request**: compartir la transacción retenía el lock de la fila `(empresa_id, tipo)` hasta el commit y serializaba todas las altas de la empresa (p95 1034–1092 ms con 50 meseros, `docs/explain-orders.md`). El `empresa_id` sigue saliendo del JWT. Se acepta un **hueco** en la numeración si la creación falla después de reservar el folio: un folio sin comanda es preferible a una cola de un segundo en el pico.
- [2026-10-28] **Estados de mesa derivados.** `PATCH /tables/:id/status` solo acepta `LIBRE` y `MANTENIMIENTO`; `OCUPADA` y `RESERVADA` los escriben las órdenes y las reservas. Una mesa con orden abierta o reserva activa no se bloquea ni se da de baja (409). La baja de mesa es lógica (`deleted_at`) y el trigger `soft_delete_row` queda como respaldo.
- [2026-10-28] **Reservas con aforo y ventana de ±90 min.** `POST /reservations` rechaza con 409 si `nro_comensales > mesas.capacidad` o si la misma mesa tiene otra reserva activa a menos de 90 minutos. Editar solo se permite en `POR_CONFIRMAR`; los estados terminales (`EJECUTADA`, `CANCELADA`, `NO_SHOW`) no se reabren. `GET /reservations?fecha=` filtra el día completo en hora de Lima (UTC-05:00 fijo, sin DST), no en UTC.
- [2026-10-28] **`ADMIN_GLOBAL` indica `sucursalId` en mesas; los demás roles lo heredan del JWT.** El token del admin no trae sucursal (opera la empresa), así que `POST /tables` acepta `sucursalId` en el body y `GET /tables` en la query; el servicio valida que la sucursal sea de su empresa (404 si no) y rechaza que un rol atado a sucursal pida otra (400). No se usa un header global: el tenant de RLS sigue saliendo del JWT y la sucursal solo acota la operación.

- [2026-10-28] **AYCDS-20 — El precio de la comanda lo pone el servidor.** `CreateOrderDto` ya no acepta `precioUnitario`: con `forbidNonWhitelisted` un body que lo envíe da **400**. `OrdersService` resuelve platos con `PricingService.resolvePrice` sobre la lista indicada (o la activa) y combos con `combos.precio_fijo`, valida que el plato/combo exista y esté activo, y calcula `subtotal`/`total` en el servidor con 2 decimales. El `mesero_id` sale del JWT (nunca del body) y `numero_orden` de `SequencesService`. La mesa pasa a `OCUPADA` al crear y se libera en la misma operación al llegar a un estado terminal.
- [2026-10-28] **AYCDS-20 — `ANULADA` solo desde `POR_CONFIRMAR`.** Una comanda que ya entró a cocina (`EN_COCINA`) o está `LISTO` no se deshace: se entrega y se compensa. La API responde **400** fuera de esa transición y el trigger `trg_ordenes_inmutable` (migración `20261028120000_ordenes_anulacion_estricta`) lanza `DB_ORDEN_ANULACION_TARDIA` como última línea. `PAGADA`/`CERRADA`/`ANULADA` son terminales y devuelven **409**. Cada alta y cada cambio de estado se registra en `auditoria`.
- [2026-10-28] **AYCDS-20 — La sucursal de la orden se deduce de la mesa.** Un rol atado a sucursal usa la del JWT (e indicar otra da 400); `ADMIN_GLOBAL` la toma de la mesa o de `sucursalId` en el body, y sin mesa ni sucursal recibe 400. La mesa se resuelve con el filtro de tenant, así que una mesa ajena da 404 antes de escribir nada.

- [2026-10-28] **AYCDS-14 — El WebSocket usa un ticket efímero, no el access token.** `POST /api/v1/auth/ws-ticket` firma un JWT de **60 s** con `scope: ws`, `sub`, `empresaId`, `sucursalId` y `rol`. El navegador lo obtiene del BFF (`GET /api/session/ws-ticket`, `no-store`) porque el access token vive en una cookie HttpOnly. `JwtStrategy` **rechaza** cualquier token con `scope`, así que un ticket filtrado no abre la API HTTP y caduca en un minuto. Cada reconexión pide un ticket nuevo.
- [2026-10-28] **AYCDS-14 — Rooms por empresa y sucursal, sin room de empresa para operativos.** Un rol atado a sucursal entra solo a `empresa:<id>:sucursal:<id>`; un rol sin sucursal (`ADMIN_GLOBAL`) entra a `empresa:<id>`. Así nadie recibe el evento dos veces y un cliente de otra empresa no lo recibe ni adivinando el `ordenId` (`order:subscribe` valida `empresa_id`). Las emisiones usan `.to(a).to(b).emit()` (unión).
- [2026-10-28] **AYCDS-14 — Sobre único y deduplicación en el cliente.** Todo evento viaja como `{ eventId, at, data }`; el cliente descarta `eventId` repetidos con una ventana de 200 porque Socket.io puede reentregar tras reconectar. La reconexión es propia (`reconnection: false`) con backoff 1 s → 30 s + jitter y ticket nuevo por intento; sin sesión (401 del BFF) no reintenta.
- [2026-10-28] **AYCDS-14 — Sin Redis adapter por ahora.** Los rooms viven en memoria del proceso: con más de una instancia de la API hace falta `@socket.io/redis-adapter`. Queda documentado en `docs/websockets.md` como límite conocido, no como olvido.
- [2026-10-28] **AYCDS-22 — La comanda no necesitaba índices nuevos.** Con el dataset de 50k órdenes el plan de escritura ya era correcto: el costo estaba en el lock del folio y en el trabajo por request. Además del folio en autocommit, se juntaron los cuatro `set_config` del contexto RLS en una sola sentencia y la resolución de precios pasó de 2 consultas por línea a 3 consultas por comanda (platos, combos y `precios_platos` en lote). `DATABASE_POOL_MAX` (default 10) queda como perilla: subirlo a 20 no mejoró nada con la base ociosa, así que no se cambia el default. Evidencia y reproducibilidad en `docs/explain-orders.md`.
- [2026-10-28] **AYCDS-22 — Lectura del KDS bajo RLS: deuda conocida, no se tocó la seguridad.** Con `FORCE ROW LEVEL SECURITY`, el planificador no ve `pg_statistic` de las tablas con RLS si el rol no tiene `BYPASSRLS`, estima 20 % para `estado` y el listado del KDS recorre ~50 000 filas (157 ms) en vez de usar `idx_ordenes_estado` (0,075 ms con estadísticas). No se otorgó `BYPASSRLS` a `fogoneria_rls`. Opciones evaluadas en `docs/explain-orders.md` §6: rol de lectura con `BYPASSRLS`, vista `SECURITY DEFINER` con el filtro de empresa dentro, contadores denormalizados o `pg_hint_plan`. Debe resolverse antes de que la tabla acumule meses de histórico.
- [2026-10-29] **AYCDS-26 — `Table.id` sigue siendo numérico y estable.** La API identifica las mesas con UUID (`mesas.id`), pero cuentas, traspasos y `deriveTableStatus` usan `Table.id` numérico. `lib/table-mapping.ts` traduce el UUID a un entero positivo con **FNV-1a de 32 bits** y resuelve colisiones incrementando el id dentro del mismo listado. No se cambia el tipo ni se reordena el salón entre recargas. `Table` gana `apiId` (el UUID que viaja al servidor), `branchId` y `blocked`.
- [2026-10-29] **AYCDS-26 — `MANTENIMIENTO` es un bloqueo, no un cuarto estado.** `TableStatus` se queda en `libre | ocupada | reservada` y la mesa bloqueada se muestra con `status: "reservada"` + `blocked: true`. El bloqueo/liberación usa `PATCH /tables/:id/status` (`MANTENIMIENTO`/`LIBRE`); el servidor responde 409 si hay orden abierta o reserva activa y la UI muestra el mensaje. Solo `sucursal`/`admin` ven la acción (`canChangeTableStatus`).
- [2026-10-29] **AYCDS-26 — La agenda gana `por_confirmar` y usa el día de Lima.** `ReservationStatus` agrega `por_confirmar` (estado real `POR_CONFIRMAR` de la API) para poder confirmar desde la agenda; `EJECUTADA` se muestra como “Llegó” y los terminales como cancelada/no-show. El filtro por fecha se hace con `fecha=YYYY-MM-DD` en hora de Lima (`America/Lima`, offset fijo `-05:00`) y el ISO de alta se arma con ese offset para que una reserva de 20:00 no caiga en el día siguiente.
- [2026-10-29] **AYCDS-26 — El servidor manda en el estado de la mesa.** `deriveTableStatus` devuelve `ocupada` si la API ya la reporta `OCUPADA`, aunque no exista cuenta local: así una comanda creada desde otra sesión pinta la mesa en rojo. Sin sesión se mantiene la derivación local (cuenta abierta / reserva de hoy) para el modo demo. Las mutaciones de reservas y mesas se hacen contra la API y luego se llama a `refreshTables`/`refreshReservations`; el refresco en vivo llega por `order.created`, `order.updated` y `table.status`.
- [2026-11-06] **AYCDS-30 — El tablero del KDS se mide antes de cambiar la seguridad.** La consulta se acota por sucursal, estados abiertos, ventana de 7 días y `LIMIT`, y se documenta el `EXPLAIN (ANALYZE, BUFFERS)` como `fogoneria_rls`. Solo si sigue sin usar el índice se evalúa vista/función `SECURITY DEFINER` o contadores denormalizados. No se otorga `BYPASSRLS` al rol de negocio ni se mueve el filtro de tenant fuera de RLS «para que corra rápido».
- [2026-11-06] **Las propinas se registran en `ordenes.propina`.** El cobro (AYCDS-34) conoce la propina, así que se agrega la columna `Decimal(12,2)` con `CHECK >= 0` en esa migración y el pozo diario la suma por sucursal. No se crea una tabla de pagos para adelantar AYCDS-33: una comanda = un cobro en este dominio, y el reparto por marcación solo necesita el total del día.
- [2026-11-06] **El webhook de stock (AYCDS-13) se configura por entorno.** `STOCK_WEBHOOK_URL` y `STOCK_WEBHOOK_SECRET` (firma HMAC en `X-Fogoneria-Signature`); sin URL el job registra la alerta y no envía, así el desarrollo y el CI no dependen de n8n. Si n8n no responde, el reintento es con backoff y la alerta queda en `auditoria`.
- [2026-11-06] **AYCDS-36 — El comprobante se emite sobre una comanda PAGADA.** El documento fiscal documenta un cobro que ya existe (AYCDS-34); si se permitiera emitir sobre `ENTREGADO` se podría entregar un comprobante sin dinero en caja. El índice `uq_comp_empresa_serie` es la última defensa ante dos cajas emitiendo a la vez.
- [2026-11-06] **AYCDS-36 — Una serie por tipo, con su propio contador.** `B001` (boleta), `F001` (factura) y `T001` (ticket) son filas distintas de `secuencias`: la factura y la boleta no comparten numeración, como exige SUNAT. El número se forma en `SequencesService.nextComprobante`, no en el controlador.
- [2026-11-06] **AYCDS-36 — El IGV se deriva, no se guarda.** El total de la comanda ya incluye IGV; `desgloseIgv()` calcula `base = total / 1.18` e `igv = total - base` para la respuesta y el futuro XML. Guardar tres importes redundantes abriría la puerta a que no cuadren entre sí.
- [2026-11-06] **AYCDS-36 — La anulación delega la reversión a la base.** El servicio solo cambia `estado`, `anulado_por`, `anulado_at` y `motivo_anulacion`; los triggers de AYCDS-39 insertan el egreso de caja y la entrada de stock. Duplicar la reversión en TypeScript la haría depender de que ambos caminos se ejecuten en el mismo orden.
- [2026-11-06] **AYCDS-34 — `PAGADA` solo la escribe la caja.** `PATCH /orders/:id/status` rechaza `PAGADA` con 400 y el cobro real es `POST /cash/charges`, que deja el movimiento en el turno. Si se pudiera pagar por la ruta de órdenes, la comanda quedaría cerrada sin aparecer en el arqueo. `OrdersService.markPaid()` es la vía interna que usa la caja (transición + liberación de mesa + evento).
- [2026-11-06] **AYCDS-34 — Una sola caja abierta por sucursal.** El índice único parcial `uq_turnos_abierto_sucursal (empresa_id, sucursal_id) WHERE estado = 'ABIERTO'` es la garantía real: la comprobación en el servicio da el 409 amable, el índice evita la carrera de dos cajeros abriendo a la vez.
- [2026-11-06] **AYCDS-34 — Los totales del turno se calculan, no se acumulan.** `ingresos_total`, `egresos_total`, `saldo` y la diferencia se derivan de `movimientos_caja` al cerrar; durante el turno no se denormaliza nada. Así una reversión (AYCDS-39) no deja contadores mintiendo. La propina va en `ordenes.propina` y como ingreso con concepto `Propina …`, para que el pozo de AYCDS-33 la sume sin tocar el total de la comanda.
- [2026-11-06] **AYCDS-34 — El arqueo se guarda en el turno.** `efectivo_contado`, `diferencia` y `observaciones` son columnas nuevas: sin ellas el conteo solo viviría en auditoría y la UI de caja (AYCDS-46) no podría mostrar el descuadre.
- [2026-11-06] **AYCDS-39 — La reversión se compensa, no se edita.** Al anular un comprobante (o una orden, como red de seguridad) los triggers insertan el movimiento contrario: `movimientos_caja` EGRESO por cada INGRESO de la orden y `movimientos_inventario` ENTRADA por cada SALIDA/MERMA, restaurando `stocks_sucursal`. Nunca se hace `UPDATE` sobre el histórico (append-only de AYCDS-62).
- [2026-11-06] **AYCDS-39 — El egreso entra al turno ABIERTO, no al turno del cobro.** Imputar la reversión a un turno cerrado rompería su arqueo, así que la función `fogoneria.turno_abierto()` busca el turno abierto de la sucursal y, si no existe, lanza `DB_REVERSION_SIN_TURNO` (409): primero se abre caja. Los totales del turno se calculan desde los movimientos, no se denormalizan aquí.
- [2026-11-06] **AYCDS-39 — Los puntos quedan fuera de la reversión.** Hoy nada otorga puntos (el cobro es AYCDS-34/36) y `tipo_movimiento_puntos` no tiene un valor de ajuste; inventar un `CANJE` negativo falsearía el CRM. La reversión de puntos entra con AYCDS-31 (CRM), cuando exista quien los otorgue.
- [2026-11-07] **AYCDS-38 — Toda vista se crea con `security_invoker = true`.** `fogoneria_app` es superusuario **con `BYPASSRLS`**, así que una vista creada por él se ejecuta con sus privilegios y **no aplica RLS**: las cuatro vistas del esquema inicial dejaban ver datos de otra empresa. Con `security_invoker` la vista corre como quien consulta y RLS filtra igual que en la tabla. No volver a crear vistas sin esa opción.
- [2026-11-07] **AYCDS-38 — El BI se mide en día de Lima y la propina no es ingreso.** Las vistas nuevas usan `America/Lima` (UTC-05:00 fijo) para la fecha; `v_ventas_dia` queda como histórica en UTC. La venta sale de comandas `PAGADA`/`CERRADA` y el margen es `ventas - gastos` (gastos `PAGADO`); la propina se informa aparte porque es un traspaso al personal (pozo de AYCDS-33). El importe `comprobado` se publica aparte para conciliar con SUNAT y su diferencia es un control, no un error.
- [2026-11-07] **AYCDS-38 — El restore se ensaya en una base nueva.** `db:backup`/`db:restore` trabajan con el contenedor y `docker cp` (la tubería de PowerShell corrompe binarios). `restore.ps1` se niega a restaurar sobre `fogoneria_db` y verifica conteos + vistas BI al terminar. RPO ≤24 h / RTO ≤30 min documentados en `docs/respaldo-recuperacion.md`.
- [2026-11-07] **AYCDS-38 — `session_replication_role = replica` no ejecuta los `CASCADE`.** Las claves foráneas son triggers, así que cualquier limpieza de mantenimiento (p. ej. `reset-perf.sql`) tiene que borrar las tablas hijas explícitamente. Dejar 150 000 líneas huérfanas de `detalles_orden` rompía el `pg_restore` con `fk_detalles_orden`.
- [2026-11-06] **AYCDS-33 — El pozo de propinas sale de la propina cobrada.** Se suma `ordenes.propina` del día en la sucursal (la columna que llena el cobro de AYCDS-34), no un importe escrito a mano. Un pozo por sucursal y día (índice único) evita pagar dos veces; confirmarlo es idempotente.
- [2026-11-06] **AYCDS-33 — Reparten solo los presentes.** Beneficiarios = asistencias del día en estado `PRESENTE` o `TARDANZA`; una `FALTA` no cobra. El reparto es exacto al céntimo (`repartirPropinas`: base truncada y residuo de a un céntimo), así la suma de los repartos siempre cuadra con el total del pozo.
- [2026-11-06] **AYCDS-33 — La marcación es un upsert por empleado y día.** El índice `(empleado_id, fecha)` permite corregir una marcación (por ejemplo de `TARDANZA` a `PRESENTE`) sin duplicar filas; queda una sola verdad por día.
- [2026-11-06] **AYCDS-33 — El plan de turnos se puede borrar.** A diferencia de la contabilidad, el plan es operativo: `DELETE /staff/shifts/:id` lo quita porque no deja rastro financiero. Los pozos, una vez calculados, no se borran: se confirman.
- [2026-11-06] **AYCDS-31 — El segmento se deriva de las visitas, no se acumula.** `visitas` = comandas `PAGADA` del cliente y el segmento sale de los umbrales de `config_lealtad` (`FRECUENTE` ≥5, `VIP` ≥20 por defecto). Recalcular desde la fuente hace el proceso idempotente: repetirlo no infla nada y corrige desvíos históricos.
- [2026-11-06] **AYCDS-31 — Los puntos se otorgan en un worker, no en el cobro.** `POST /cash/charges` no debe fallar porque el CRM tenga un problema: un cron cada 5 minutos busca comandas `PAGADA` con cliente y sin movimiento `GANANCIA`, otorga `total × puntos por sol` y recalcula visitas y segmento. `POST /crm/process` permite reprocesar a mano (admin).
- [2026-11-06] **AYCDS-31 — El movimiento de puntos guarda el importe en positivo.** El signo lo da el tipo (`GANANCIA` suma, `CANJE`/`CADUCIDAD` restan) y el saldo del cliente siempre se recalcula desde los movimientos, así no se desincroniza. Un canje mayor que el saldo se rechaza con 400.
- [2026-11-06] **AYCDS-31 — Ajustar puntos exige sucursal.** `movimientos_puntos.sucursal_id` es obligatorio: el rol operativo usa la del token y `ADMIN_GLOBAL` debe indicarla en el body (misma regla que mesas y gastos).
- [2026-11-06] **AYCDS-17 — Un gasto pagado en efectivo sale de la caja.** `POST /expenses/:id/pay` con `EFECTIVO` exige turno abierto, inserta el `EGRESO` en `movimientos_caja` con `gasto_id` y marca `pagado_en_caja` + `turno_id`. Con `TARJETA`/`TRANSFERENCIA`/`YAPE` solo cambia el estado: el banco no está en el cajón y el arqueo no debe descuadrar. - [2026-11-06] **AYCDS-17 — El gasto pagado en caja no se edita.** La base ya lo bloquea (`DB_GASTO_PAGADO`); el servicio devuelve **409** con el motivo antes de llegar al trigger. Un gasto mal creado se compensa con otro movimiento: la contabilidad no se borra ni se reescribe.
- [2026-11-06] **AYCDS-17 — El pago es idempotente por estado.** Se lee `estado_pago` y el `updateMany` exige `PENDIENTE`; si dos cajas pagan a la vez, la segunda recibe **409** y el egreso no se duplica (el primero ya está en el turno).
- [2026-11-06] **AYCDS-11 — El kardex se descuenta al `ENTREGADO`, no al crear.** La comanda puede anularse hasta `POR_CONFIRMAR` y la cocina puede rechazar platos; descontar al crear obligaría a reversas que nadie pidió. Al entregar, la receta ya se consumió de verdad. El descuento corre **dentro de la transacción del request**: si el kardex falla, la entrega no se confirma.
- [2026-11-06] **AYCDS-11 — El stock no baja de cero.** `stocks_sucursal` tiene un `CHECK` que prohíbe negativos, así que el faltante se refleja como stock 0 y el `movimiento_inventario` guarda lo realmente consumido (la diferencia se ve al reponer). - [2026-11-06] **AYCDS-11 — Sin receta no se bloquea la entrega.** Un plato sin escandallo se omite y se reporta en `sinReceta`; la cocina no deja de servir porque falte una receta. Los combos se expanden con `combos_platos.cantidad` antes de explotar la receta de cada plato.
- [2026-11-06] **AYCDS-11 — El consumo es idempotente por `SALIDA`.** Si la orden ya tiene un movimiento de salida no se vuelve a descontar: `ENTREGADO` no se repite, pero un reintento del cliente sí puede llegar.
- [2026-11-06] **AYCDS-19 — El descuento lo calcula el servidor, no el cliente.** `POST /orders` ya **no** acepta `descuento`: recibe `cuponCodigo` y `PromotionsService.resolverCupon()` valida (activo, vigente, usos), calcula el importe y lo descuenta del total.
